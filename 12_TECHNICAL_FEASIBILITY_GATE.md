# Technical Feasibility Gate — experimental

## Trigger
Apply when all are substantially true:
1. the commercial thesis depends on a technical capability that is not ordinary implementation work;
2. failure of that capability would collapse the differentiated value or economic justification;
3. public evidence does not establish that the required inputs contain enough signal or that the mechanism can perform at a useful level;
4. a cheap pre-build test can materially reduce this uncertainty.

## Behavior
- Flag `FEASIBILITY_REQUIRED` in the research report.
- Do not confuse buyer pain with proof the technical mechanism works.
- Do not assume impossibility merely because the target variable is not directly observable; statistical prediction may still work.
- Specify the smallest retrospective/prospective falsification experiment.
- Freeze success/failure thresholds before testing.
- Compare against the strongest cheap incumbent/manual baseline.
- Measure false positives and false negatives where relevant, not only headline accuracy.
- Ask whether success would actually change workflow/economics, not merely produce an interesting prediction.

## Verdict interaction
Technical uncertainty alone is not KILL. It may block a confident RESEARCH_PASS when the uncertain capability is the only differentiated value-producing mechanism. If a feasibility test is required before meaningful buyer validation, say so explicitly and do not recommend building the full product.
